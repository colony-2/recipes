# What changed after the four-job review

A person can approve a plan once and still ask to see the result. If the same plan comes back for approval, the delegate compares the proposed work with what the person actually saw and said. It can reuse that receipt, send a small fix to the author, or explain the new choice to the person. Reuse preserves the original stopping point and the documents the person approved.

| What the person or agent does | What happens now |
| --- | --- |
| Replies to a review | Questions and edits stay in the same thread. The title names the proposal. The next message answers the question or explains the edit. Both approval choices accept optional guidance. |
| Requests work an owner has agreed to | The author selects the recorded negotiation by its report folder ID. Delivery uses the accepted assignment and remembers the child job. Nested owners return their agreement to the requester. |
| Needs information from another cell | The guide gives examples for reading available source, asking about a private interface, requesting a change and reporting a suspected bug. A conversation can end with the answer. |
| Hits a consultation or repair limit | A conversation has four rounds by default. A phase can start ten distinct conversations, including nested ones. At a limit the delegate sees which request stalled. It can return one specific local repair after ordinary returns are spent. |
| Reviews a standard proposal | The 1P opens first, followed by Design and Tests. The prompts supply the document outlines and ask the author to explain revisions. A consultation-started proposal links to the request that led to it. |
| Requests a routine compatible update | Direction can hand Implementation a short summary. The first human review is the verified Outcome. A migration or a material new commitment goes through Preparation. |

A review reuses descriptions for unchanged attachments. A missing optional link leaves the delegate’s question readable. A missing primary document gets a repair turn. Recovery checks the recorded decision, and integration still checks the candidate and its verification inputs.

The recipe emits ordered native review requests and submissions. Cortex owns how clients display that history. The review/v2 form still sends its required empty conversation field. The recipe keeps the approval receipt and attachment references it needs to resume.
