# Approve notebook bug fix: preserve the final note without a trailing newline

Users can silently lose the final note when importing a hand-edited text file. **Owning cell:** **`notebook`. Kind of work: bug. Decision needed now:** approve a change limited to retaining the final nonempty segment in the text importer, with regression coverage for the existing blank-line and Unicode behavior. Implementation remains pending this direction review.

## Problem Description

The [submitted request](request.md) reports unexplained final-note loss. The repository already promises that a nonempty final line is imported whether or not it ends with a newline (`README.md:14–16`; [source snapshots](evidence/repository-context.md)).

The failure is reproduced through the CLI: a UTF-8 file containing `First\nSecond` prints `["First"]`, exits with code 0, and emits no warning. Adding a trailing newline prints `["First", "Second"]`. A single unterminated note, `Only`, produces `[]`.

The parser unconditionally discards its final LF-delimited segment (`import_notes.py:7`). That segment contains a note when the file lacks a trailing newline. Both existing tests pass because their inputs end with newlines. [Reproduction and compatibility evidence](evidence/reproduction.md) contains the commands, observed results, and links to raw evidence.

## Non Goals

Changes to the web editor, storage APIs, persistence, import format, whitespace policy, Unicode normalization, encoding policy, JSON formatting, or error reporting are outside this fix. Recovering notes from past imports and investigating which editors omit final newlines are also outside scope.

## What we are planning to do

After approval, update `parse_notes` to retain every nonempty LF-delimited segment, including the final one. Keep its existing empty-segment filter and the CLI's UTF-8 reading and JSON output behavior. The filter already handles the empty segment produced by a trailing newline.

Add focused regression coverage in `test_import_notes.py` for missing final newlines and the compatibility cases established by this investigation, then run the existing suite and verify the CLI reproduction is corrected. The expected implementation boundary is `import_notes.py` and its tests; the README already states the intended behavior.

## Compat/Upgrade

No migration, dependency, API, or command change is needed. For already terminated inputs, results should be unchanged. For unterminated inputs, the intended difference is inclusion of the final nonempty note. Empty files and truly empty lines still yield no additional notes; spaces and tabs remain note content. Unicode characters and the JSON serialization convention remain intact.

The CLI currently normalizes CRLF and CR line endings through its text reader. Direct parser calls split only on LF and retain embedded CR characters. Preserve both behaviors. Downstream consumers may see one more note for affected inputs; that is the documented result previously lost.

## Key challenges/design questions & answers

| Question                                                                        | Answer                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What is established, and what remains uncertain?                                | The missing-final-newline failure is reproduced in the parser and CLI, including a single-note file and UTF-8 text. No original user file was supplied, so we cannot attribute every report to this cause or identify a particular editor. That uncertainty does not prevent this bounded correction.                                                                                         |
| Why is this a bug rather than a format change?                                  | The README explicitly accepts an unterminated final note. The observed output violates that existing contract.                                                                                                                                                                                                                                                                                |
| What is the smallest appropriate correction?                                    | Stop unconditionally excluding the final segment while preserving LF splitting and the nonempty filter. This addresses the confirmed cause without adding another parsing rule.                                                                                                                                                                                                               |
| What does preserving blank-line behavior mean?                                  | Ignore zero-length segments at the beginning, middle, or end, including repeated empty lines. Preserve whitespace-only segments such as spaces and tabs because they are currently nonempty notes. An unterminated whitespace-only final segment must likewise be retained. Trimming would change that policy.                                                                                |
| Why avoid replacing the parser with `splitlines()`?                             | A local probe shows it splits U+0085, U+2028, and U+2029 inside text that currently forms one note. Keeping LF splitting preserves Unicode content and existing control-character behavior.                                                                                                                                                                                                   |
| What must remain true for Unicode?                                              | Retain UTF-8 decoding, exact note text, combining characters, emoji, and embedded Unicode separators. Preserve the existing escaped JSON representation; compare decoded content when verifying Unicode round trips.                                                                                                                                                                          |
| Do CRLF or CR files require a wider change?                                     | No. CLI fixtures confirm its existing text-reader normalization; those files show the same missing-final-note bug when unterminated. Direct parser CR preservation is a separate existing behavior to retain.                                                                                                                                                                                 |
| What evidence supports the direction, and what will establish completion later? | The two baseline tests pass. The diagnostic script records 37 observations, including 12 contract mismatches, all involving unterminated final segments; these include overlapping parser and CLI cases. After implementation, the reproduced losses must be corrected, compatibility observations preserved, and the suite pass. Baseline findings are not validation of an implemented fix. |
| Does another cell need to agree to a change?                                    | No cross-cell behavior changes are proposed. `PURPOSE.md` assigns the text import CLI to `notebook`, and this CLI only reads a file and prints JSON. Storage interfaces are not involved. The missing optional c2j configuration is recorded in [environment evidence](evidence/environment-discovery.txt) and does not block this local direction review.                                    |
| What is the outstanding decision?                                               | Approve this importer-and-tests scope before implementation. No additional product decision is unresolved by the repository contract or observed behavior.                                                                                                                                                                                                                                    |
