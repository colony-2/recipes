# Product choices for recovering recent drafts

Storage agrees the feature boundary in [its handoff](work/handoff.md). These choices remain visible for human review; the recommendations below are proposed defaults, not recorded human decisions. The counting interpretation and save cadence materially affect whether the resulting recovery window is useful.

| Choice or question | Recommendation | Consequences and evidence |
| --- | --- | --- |
| Does “last three saved versions” include current? | Offer three **earlier** versions plus current (`H = 3`), because the task is recovery after overwrite. Confirm this interpretation. | Four total snapshots, at most 256 KiB raw text. Three total saves (`H = 2`) is a smaller alternative at 192 KiB but offers only two older choices. No current retention policy exists in code. |
| Does every successful save count, including identical text? | Yes, preserve today's version semantics and capture every commit. | The model increments versions for identical text. Frequent unchanged saves can evict useful differences quickly. Retaining three distinct texts is a different policy; notebook may separately avoid unnecessary saves but old clients could still send them. Confirm the desired meaning before changing semantics. |
| Is a count bound sufficient, or is a time window required? | Count-only retention, without time expiry; no minimum recovery duration. | A quiet draft retains versions indefinitely until more saves or deletion. Rapid saves can exhaust recovery immediately. Three versions cannot guarantee “yesterday's draft.” A time-window or autosave-coalescing requirement needs a different bound and explicit storage policy. |
| What happens when restoring over a concurrent edit? | Keep optimistic concurrency and return 409; the client preserves unsaved text and asks the user to resolve the competing state. | Existing clients already use version preconditions. Automatic reload-and-retry would deliberately overwrite the newer edit. A restore uses the head version being replaced, never the historical version. No automatic merging is proposed. |
| Are empty drafts valid history? | Yes. Keep successful empty saves and allow their restoration. Exclude absent version zero. | Empty text is already valid; saving it increments the version. Dropping empties silently would make “successful save” inconsistent. Empty text must not become a deletion instruction. |
| How are large drafts handled? | Retain the existing 65,536-byte UTF-8 ceiling. Return up to three historical texts in one bounded read. | Exact boundary and multibyte behavior passed probes. Larger drafts remain rejected without mutation. Metadata-only listing plus a content read would reduce payload but add an interface; reconsider only with measured transport constraints. JSON encoding adds wire overhead. |
| How do older API clients participate? | Capture history server-side for all successful existing PUTs; leave old request/response bodies and errors unchanged. | No upgrade or flag needed. Their saves, including repeated or empty text, also advance retention. Old clients do not gain a history UI automatically. |
| Does a lost response mean the save failed? | Count a committed save and keep the existing read/compare recovery guidance. | Retry with the old version conflicts. Identical current text establishes content equality, not which request caused it. Exactly-once attribution would require additional scope. |
| What survives deletion or reset? | Follow the existing draft lifecycle and remove its history when that lifecycle removes the draft, unless a different product requirement is agreed. | No delete/reset API is present in this checkout. Storage must inspect the real lifecycle before finalizing integration; this proposal adds no delete or undelete feature. |
| Can users recover old content immediately at launch? | Make the limitation explicit: only the current saved value and versions captured from rollout onward are available. | The current model has already discarded previous text. Existing backup/revision mechanisms, if any, require separate evidence before promising backfill. |

The actual durable backend is an integration input, not a product preference that can be inferred from this fixture. It must be identified before implementation can demonstrate the cross-device and restart requirements. No backend-specific claim or implementation choice is made here.

Evidence: [source inventory and local checks](evidence.md). Notebook interaction design and its own agreement remain separate from storage's scope.
