# Reuse the draft API; address overlapping-write atomicity

Users lose unfinished notes when switching notes. Notebook asked storage whether the existing draft API can support saving while typing, manual Save, clear status, two tabs, lost responses, conflict recovery, and size limits. This is advice for direction approval; no implementation or deployment was performed.

**Recommendation:** retain `GET /drafts/{id}` and `PUT /drafts/{id}` with `{text, version}`. No autosave endpoint, schema migration, or idempotency-key feature is needed for the proposed workflow. The documented contract provides version checks, HTTP 409 on stale writes, exact stored text, missing-note version zero, and a 65,536-byte UTF-8 text limit inclusive of the boundary. Notebook must serialize its own writes, retain immutable submitted text and subsequent edits, and reconcile uncertain outcomes through a fresh GET. See [findings](findings.md).

**Concurrency qualification:** the supplied pure model does not make its version check and assignment atomic. Both existing tests pass, but they only exercise sequential writes. Three controlled overlapping-call trials each returned two successes at version 1 for different texts submitted at version 0, leaving only one text stored. This is a model bug under overlapping calls; it is not evidence that a particular deployed server allows that schedule. No HTTP server or execution model is supplied. A UI-only rollout cannot be endorsed as safe across simultaneous tabs without verified server serialization or atomic compare-and-write. See [source evidence](evidence/sources.md) and [probe output](evidence/probe-output.txt).

Storage agrees a bounded **bug** follow-up: make compare-and-write atomic for concurrent calls sharing a Drafts instance, preserve the existing API contract, and add meaningful concurrency regression coverage. The receiver-authored [handoff](work/handoff.md) is ready for the coordinator and remains conditional on the requested direction approval. This is an agreement on future scope, not permission to implement now. Production concurrency and read consistency must also be checked against the actual serving layer when available; an in-process guard alone does not establish multi-worker guarantees.

Notebook owns autosave scheduling, request/note identity, recovery, accessible status, and guarded switching. Suggested 800 ms idle debounce / 5 s maximum dirty interval is a reasonable provisional UI policy; there is no documented rate limit or performance guarantee. Unsent text remains browser memory only in the requested online scope.

Alternative: if the actual serving layer already serializes every writer to the same authoritative draft, no deployment storage change is necessary. Record that evidence before removing the concurrency prerequisite. A second endpoint would neither fix the demonstrated race nor preserve unsent browser text.

Remaining unknowns are HTTP error body schemas (including 409), oversize/encoding status codes, cache and read-consistency guarantees, ID rules, request-level limits, authentication/throttling behavior, and deployment topology. These are not grounds to invent interfaces. They are explicit integration checks for the review; local facts and recommended defensive behavior are separated in the findings. No unresolved human choice is required to answer this consultation; notebook's requested direction approval remains with its coordinator.

Evidence: [source snapshots](evidence/sources.md), [existing test run](evidence/baseline-tests.txt), [reproducible advisory probe](evidence/probe.py), [observations](evidence/probe-output.txt). The probe intentionally demonstrates a safety violation; its successful execution does not mean concurrency safety passed.
