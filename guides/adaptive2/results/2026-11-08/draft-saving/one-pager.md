# Approve notebook feature direction: autosave with guarded navigation and conflict recovery

Users lose unfinished notes when they open another note. **Owning cell: notebook. Kind: feature**, with a storage-owned concurrency bug dependency. **Decision needed now:** approve saving while typing through the existing draft API, a guarded note switch, and explicit recovery that preserves text. Also approve the bounded storage fix as a prerequisite to claiming safety across two tabs. This is a direction review, not implemented behavior or a detailed specification.

**Recommendation:** reuse GET/PUT; do not add an autosave endpoint. Keep manual Save. Prefer a short wait when switching notes over silently abandoning a draft. Keep unsent text in this tab and offer download/copy; durable offline recovery remains excluded.

Review the [proposed interactive UI](mockup.html), [storage consultation summary](coordination/request-0-0/artifacts/iter1/consultant/summary.md), and [full storage findings](coordination/request-0-0/artifacts/iter1/consultant/findings.md). The mockup has selectable normal, slow, failure, uncertain-response, conflict, size, and load-failure scenarios. All saves in it are simulated.

## Problem Description

The current notebook replaces the editor on Open without first preserving unfinished text. A single shared version and status also allow a response for older text to say Saved after the user has typed more. The navigation field doubles as the save destination, so changing it can send one note's text to another note. These three behaviors were reproduced against the unchanged inline script using controlled responses; see [repository review and checks](evidence/repository-review.md).

The goal is to make ordinary online editing and switching dependable: users know whether their current text is saved, can recover after a failure, and never have an old response or another tab silently replace their work. Notebook owns this interaction. Storage owns the conditional write contract and its enforcement.

Storage confirmed the existing API is intended for frequent draft saves. It also reproduced a separate model bug: two overlapping writes using the same version can both succeed and one accepted text disappears. Its two existing sequential tests pass; three controlled concurrent trials expose the race. This finding changes the provisional UI-only direction into a notebook feature with a bounded storage bug dependency. It does **not** establish that any deployed server permits that schedule, nor that deployment serialization already prevents it. There was no previously approved direction to revise.

## Non Goals

* Offline editing, localStorage/IndexedDB drafts, background sync, automatic crash/reload recovery, or a promise to save during browser close.

* Collaboration, live presence, automatic merging, cross-tab leader election, or a shared multi-user editing experience. Accidental concurrent tabs must still be safe.

* A new autosave endpoint, idempotency-key service, last-write-wins mode, version history, deletion, rename, or note-management redesign.

* Changing the import CLI, creating a new HTTP service or persistence backend, or implementing/deploying anything in this review.

## What we are planning to do

1. **Notebook:** track the loaded note separately from the navigation target; retain its current text, last confirmed baseline, and immutable submitted text. Add autosave after a short pause, a consistent manual Save action, and visible status tied to the current text.
2. **Notebook:** keep one write active for a note, coalesce later edits, and guard switching until the current draft is confirmed. Failures leave the editor intact with retry/check, comparison, and download/copy actions. Fetching another note must also succeed before the old editor is replaced.
3. **Notebook:** pause autosave on a version conflict and show local and stored copies separately. Let the user prepare a reviewed draft without replacing their original text. Save that result conditionally; a further conflict returns to comparison.
4. **Storage, after approval:** repair the demonstrated overlapping-write bug within the existing model/API and verify it with competing-writer coverage. Preserve the receiver-authored [bug handoff](coordination/request-0-0/artifacts/iter1/consultant/work/handoff.md); this review neither rewrites nor executes it.
5. **Before release:** verify the actual serving layer's atomic version enforcement, authoritative reconciliation reads, persistence guarantees, and error mapping. Notebook behavior and the model fix can be developed after approval; release with a two-tab safety claim depends on these integration checks. If broader storage/deployment work is required, obtain a revised receiver-owned scope rather than silently expanding this fix.

The [mockup](mockup.html) makes the proposed interaction reviewable, including a keyboard-accessible switch dialog, persistent manual Save, explicit saving/failed/conflict labels, and a separate comparison workspace. [Validation evidence](evidence/validation.md) records the checks actually run and their limits.

## Compat/Upgrade

Retain `GET /drafts/{id}` and `PUT /drafts/{id}` with `{text, version}`. Reads return `{text, version}`; successful writes return the updated draft. A successfully read missing note has empty text and version 0. A failed read must never be treated as an empty new note. Reuse returned versions rather than predicting them. No route or schema migration is proposed, and manual Save continues to work through the same conditional-save path.

The inclusive limit is **65,536 bytes of UTF-8 text**, not characters or total JSON size. Empty text is valid. Existing notes remain usable; no truncation or normalization is introduced. The storage fix preserves these behaviors. Existing clients beyond the supplied notebook were not available to audit.

The storage checkout is a pure in-memory model, not a deployed HTTP service. No task connection metadata was available: `c2j self`/`cells` require an absent config, and this CLI lacks the job-inspection command. These facts limit release claims, not the direction decision. A model lock is not evidence of safety across independent server workers or durable storage. Integration checks remain explicit below.

## Key challenges/design questions & answers

| Question                                                                               | Answer / recommended decision and reason                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Scope — Is this a feature, bug fix, or broader coordination project?**               | Keep the parent classified as **feature**: users gain autosave and recovery states. Notebook owns it; the storage atomicity **bug** is a dependency. The demonstrated existing UI flaws are addressed within that feature. No separate importer or platform project is implied.                                                                                                                                                                                                                                                                                                                                                                                      |
| **API — Is a new autosave endpoint necessary?**                                        | **No.** Storage confirms the existing GET/PUT interface already supports frequent conditional saves. A second endpoint would not preserve unsent browser text or fix overlapping-write atomicity. Use the documented interface; [consultation](coordination/request-0-0/artifacts/iter1/consultant/summary.md) records the agreement.                                                                                                                                                                                                                                                                                                                                |
| **Storage — Can this safely ship as UI-only work?**                                    | Not on current evidence. The model lets concurrent writers both pass the same version check. Approve the narrow [storage bug handoff](coordination/request-0-0/artifacts/iter1/consultant/work/handoff.md) and require atomic compare-and-write across all authoritative writers at release. A proven globally serialized serving layer could make a deployment storage change unnecessary; it does not retroactively prove the model is thread-safe. An in-process fix alone does not establish multi-worker guarantees.                                                                                                                                            |
| **Cadence — When does typing trigger a save?**                                         | Recommend **800 ms after an idle pause**, with a **5 s maximum dirty scheduling interval** during continuous typing when eligible to send. These are provisional UX defaults, not a service SLA. Do not send unchanged text, exceed one active write to satisfy the timer, or submit half-composed IME input; save after composition ends. No documented storage rate limit or latency target was found. Validate load/latency before launch.                                                                                                                                                                                                                        |
| **Manual Save — What does the button do, including repeated clicks?**                  | Keep Save visible. It immediately requests the newest eligible draft through the same queue, bypassing debounce. During a write, a click queues the newest edits once; it must not start a parallel write. Disable Save with an explanation when nothing changed, the initial load is unresolved, text is invalid/oversized, or conflict resolution is required. Offer Ctrl/Cmd+S within the editor as the same action, without trapping shortcuts elsewhere.                                                                                                                                                                                                        |
| **Identity — Which note does a save belong to?**                                       | The loaded note ID is authoritative, independent of the editable “Open note” target. Tie each request and response to its captured note, version, and text. Ignore obsolete read responses. Never send A's text to B because the user changed the navigation field, and never let A's response change B's status or baseline.                                                                                                                                                                                                                                                                                                                                        |
| **States — What does each visible label mean?**                                        | **Unsaved changes:** current text differs from the confirmed baseline, waiting to send. **Saving…:** a captured version is in flight; show “Newer edits waiting” if applicable. **Saved:** current text is confirmed by a valid write response or authoritative reconciliation; show the time of confirmation. **Couldn't save:** a known rejection or exhausted recovery requires action. **Couldn't confirm save:** the server may have accepted a request whose outcome is unknown. **Conflict:** different stored text requires review; autosave is paused. Slow/size/load messages supplement these meanings, rather than turning every error into Save failed. |
| **Saved — Is it a permanent promise or a response for older text?**                    | It describes the current local snapshot at its last confirmation, not a guarantee that no other tab will later change the note or that unsent text survives a crash. If the user types while an older snapshot is saving, acknowledge that snapshot's version and keep the newer text dirty. Never replace the textarea from the response or label those newer edits Saved. Verify persistence behavior before presenting production saving guarantees; the supplied in-memory model cannot prove durability.                                                                                                                                                        |
| **Switching — Can users move to another note while saving?**                           | Recommend a **guarded switch** for this first version. On Open with dirty, in-flight, or unresolved work, show “Save before opening \[target]”; Save & open flushes and waits for confirmation, and Keep editing cancels only the navigation intent. Do not navigate just because an older snapshot finished. This deliberately trades a possible short delay for simpler, visible recovery and bounded retained state; background queues across many notes are deferred.                                                                                                                                                                                            |
| **Switch failure — What if saving or opening the target fails?**                       | Stay on the original note with text intact. A blocked save offers retry/check, comparison if needed, and download/copy. A failed target GET leaves the original editor and confirmed baseline intact and says which note could not open. Do not offer a one-click discard-and-leave path in this first version. Download is an escape to external recovery, not proof that the note was saved or permission to navigate automatically.                                                                                                                                                                                                                               |
| **Switch cancellation — May the user keep typing?**                                    | Normal saves never lock the editor. The switch dialog temporarily takes focus; Keep editing/Escape returns focus to the Open control and cancels pending navigation while an already-started save may finish. Retain newer local edits. Late completion must not reopen a canceled destination. Disable repeated conflicting navigation intents while the dialog is active.                                                                                                                                                                                                                                                                                          |
| **Slow requests — How long do we wait?**                                               | Recommend “Still saving…” after **5 s** and an uncertain-outcome recovery state after about **15 s**, with keep-editing and export available. These are tunable interface thresholds. Aborting client waiting does not roll back a server write. Keep the immutable attempt and reconcile before proceeding; never overlap ordinary writes to make the UI appear faster.                                                                                                                                                                                                                                                                                             |
| **Retry policy — Should retries continue forever?**                                    | No. For transient network/service problems, recommend at most **two automatic recovery attempts** with backoff around 2 s and 5 s plus jitter, honoring Retry-After when supplied. Reconcile first if a write may have committed. Then pause with an explicit Retry/Check saved version action. Manual retry starts another bounded attempt without dropping text. Do not retry unchanged invalid/oversized text, permissions failures, or genuine conflicts automatically. These are direction defaults pending actual adapter behavior.                                                                                                                            |
| **Lost response — How can a committed save be recognized?**                            | Preserve immutable submitted text **and** newer local edits. Fetch the same note from the authoritative source. If returned text exactly equals the submitted snapshot, adopt the returned baseline/version; show Saved only if the editor still represents that snapshot. Otherwise keep newer edits queued. Equality proves that content was stored at the read, not who wrote it or that it can never change again. Exact storage text is supported by the model; transport fidelity and fresh reads need integration verification.                                                                                                                               |
| **Lost response — What if GET differs, fails, or the first request is still running?** | If stored text differs at a newer version, pause for comparison; never take that version and blindly resubmit. If a fresh read still shows the original version/baseline, retrying the original attempt with its original expected version is safe **only with atomic enforcement**: at most one attempt can win. A failed/stale/invalid read leaves saving unconfirmed. Unexpected version rollback or inconsistent text/version also stays unresolved. A client no-cache option alone does not prove an authoritative read.                                                                                                                                        |
| **Idempotency — Do retries require a new key or endpoint?**                            | Not for this direction. A repeated PUT with the original version may return 409 after the first committed; that is an outcome to reconcile, not permission to overwrite. Writing identical text again with a current version still increments the model's version. Avoid redundant writes once content is confirmed.                                                                                                                                                                                                                                                                                                                                                 |
| **Two tabs — What is guaranteed without collaboration?**                               | Both tabs retain their own drafts. With atomic storage writes, only one write can succeed for a given expected version; the loser enters recovery instead of replacing the winner. A per-tab queue cannot provide this guarantee on its own. On return to a tab, a fresh check can indicate a newer stored version without injecting it into the editor; pause dirty work for comparison. Do not add polling, cross-tab leadership, or automatic merging to this scope.                                                                                                                                                                                              |
| **Conflict — What happens after HTTP 409?**                                            | Do not assume a particular 409 JSON body or copy its version into a retry. Fetch stored text for comparison and retain local text unchanged. If the stored content equals the attempted snapshot, reconcile as above; otherwise show “Another version was saved” with Review differences and Download my draft. A failed comparison read leaves the conflict and local text intact.                                                                                                                                                                                                                                                                                  |
| **Recovery — How can users resolve a conflict without overwriting either text?**       | Show read-only **Your draft** and **Stored version**, plus a separate **Reviewed draft** workspace. Copying either side as a starting point affects that workspace only. The user can combine text or choose a side explicitly, then Save reviewed draft conditionally against the version they reviewed. Retain original local text and the compared copy until the reviewed save is confirmed and the user closes review; export is always available. This is an explicit replacement decision, not an automatic merge or force-save.                                                                                                                              |
| **Recovery races — What if typing or another tab changes things during comparison?**   | Editing the original cancels/invalidate the pending comparison choice; refresh the “Your draft” snapshot before another reviewed save. If stored text changes again, the conditional reviewed save conflicts and the user reviews the new version. Do not silently rebase a chosen replacement. Keep original and reviewed text available through failures.                                                                                                                                                                                                                                                                                                          |
| **Browser close/reload — What survives?**                                              | Only text acknowledged by the real persistence layer, or a copy the user actually exported. Current unsent text and comparison snapshots are **memory-only**. Register a leave warning only while dirty/in flight/unresolved, but do not rely on it: browsers may not show it on crash/mobile termination. Saving on close or sendBeacon cannot be the correctness mechanism. Download/copy is the recovery option in the approved online scope; automatic durable local recovery would require a later direction change.                                                                                                                                            |
| **Connectivity — Does retaining text imply offline editing?**                          | No offline mode or sync queue is promised. A connection failure leaves already-entered text visible and recoverable in the current tab, with saving paused/unconfirmed. Reconnection requires reconciliation and a bounded retry. Do not clear text when connectivity drops, claim it is safely stored on this device, or persist it in browser storage.                                                                                                                                                                                                                                                                                                             |
| **Size — What is the limit and how should it appear?**                                 | **65,536 UTF-8 bytes inclusive**, confirmed at both ASCII and emoji boundaries. Count the exact submitted text, not JavaScript character count or the entire JSON body. Show a byte counter, emphasize approaching the limit at about 90%, and on excess show the exact overage, block sends, preserve the full text, and offer export/reduction. Never truncate pasted text. An older in-flight valid save does not make a newer oversized draft Saved.                                                                                                                                                                                                             |
| **Text fidelity — What about Unicode, empty notes, and formatting?**                   | Empty text is a valid conditional write, not deletion. Preserve exact well-formed Unicode, whitespace, and line endings in captured snapshots. Do not normalize silently. Detect invalid surrogate sequences before sending; retain the original and explain correction rather than silently replacing invalid characters through encoding. A byte count alone does not validate Unicode. Export fidelity for unusual encoding must be verified; the mockup's normal UTF-8 download is not proof for malformed input.                                                                                                                                                |
| **First load / note IDs — When can editing and saving start?**                         | First establish a successful baseline for the loaded ID. A successful missing-note read gives empty text/version 0 and permits creation; network/parse/permission failure does not. Show a loading/error state and disable uninitialized saves. Encode IDs in routes and use them as text in UI. Production ID constraints and URL/request limits are undocumented integration facts, not a reason to invent rename/delete behavior.                                                                                                                                                                                                                                 |
| **Other errors — What if authorization, validation, or parsing fails?**                | Retain text for every failure. A malformed/lost success response is uncertain and needs reconciliation. Known validation/permission denials require user correction or access recovery rather than endless retries; if authentication requires leaving the page, offer export first. Distinguish the action to recover without exposing raw server messages as HTML. Exact HTTP error bodies, oversize status, authentication, throttling, and transport limits are **unverified**, not established features of this model.                                                                                                                                          |
| **Accessibility — Can status and recovery be understood without color or a mouse?**    | Use visible text labels, semantic buttons, descriptive field labels, strong focus outlines, and a persistent Save button. Announce meaningful state transitions through a polite live status; announce actionable failures once, not each keystroke or byte count. Preserve editor focus/caret during routine saves. Use a named modal dialog with focus containment, Escape/Keep editing, and focus return for switching; stack comparison panes on narrow screens and support zoom. Verify keyboard and screen-reader behavior after implementation; automated prototype checks are not a conformance claim.                                                       |
| **Recovery resources / privacy — How much text is retained, and where?**               | Keep a bounded set of snapshots for the single active note and its unresolved attempt/comparison, not unlimited note history. Do not evict the active oversized draft to enforce a cap or reject pasted text destructively. Avoid rendering full diffs of huge text; plain comparison/export is sufficient. Export is user initiated and must not mark Saved. Do not send note content to analytics or logs. Future resource caps beyond the API limit require explicit lossless behavior.                                                                                                                                                                           |
| **Export — What if clipboard or download access fails?**                               | Keep the draft visible and selectable. Report copy failure and offer ordinary select-and-copy as a fallback; leave Download available where supported. Starting a download does not prove the user kept the file, so neither export action may clear the draft, resolve a conflict, mark Saved, or navigate automatically. Users can deliberately close after securing an external copy, subject to the same unresolved-save warning.                                                                                                                                                                                                                                |
| **Unverified integration facts — Who resolves them?**                                  | Storage owns confirming atomicity across real writers, authoritative reads, persistence semantics, and actual wire error mapping when a serving adapter/connection is available. Notebook owns client handling and browser validation. No service/topology was supplied, and optional discovery failed in both cells. These checks are prerequisites to production claims; no human needs to choose a lock, HTTP code, or cache policy now. If the real adapter creates additional scope, return with evidence and a revised storage-owned handoff.                                                                                                                  |
| **Evidence — What has actually been checked?**                                         | Notebook reproduced three current UI failures using the unchanged script. Storage's two baseline tests passed; its advisory probes checked missing/empty notes, sequential conflict, lost-response cases, exact Unicode text, the inclusive size boundary, invalid text rejection, and reproduced the overlapping-write defect in all three controlled trials. See the [evidence index](evidence/index.md). These are model/client checks, not end-to-end results. Mockup validation is recorded separately in [validation](evidence/validation.md).                                                                                                                 |
| **Acceptance after approval — What must implementation demonstrate?**                  | Save during typing; manual flush without overlapping writes; newer edits never falsely Saved; safe guarded/canceled switching and out-of-order loads; recovery after rejection, slow requests, lost responses, and failed reconciliation; atomic competing-tab writes; repeated conflicts with all drafts preserved; exact UTF-8 boundary handling; keyboard/focus/status behavior; and a documented close/reload limitation. Confirm the real serving contract before release. These are outcome gates for the later specification, not implementation completed by this review.                                                                                    |
| **Decision — What is the human approving now?**                                        | Approve API reuse, the proposed states and guarded-switch tradeoff, memory-only recovery plus explicit export, and the storage concurrency fix dependency. Offline editing and collaboration stay excluded. The recommendations settle the product choices for this direction; the factual integration unknowns remain visible release checks. Approval permits subsequent specification/implementation planning and coordination, not an assertion that the mockup or storage fix has shipped.                                                                                                                                                                      |
